# PebbleHost Minecraft server harness

This repo lets Claude work on the files of one Minecraft server hosted on PebbleHost. Server files are reached over SFTP through `bin/mc`; there is no console or restart access yet.

## Shared background

- Glossary: `GLOSSARY.md` (`documentLanguage: en`). On term conflicts GLOSSARY.md wins; record a new term there the moment it settles, so specs, issues and code use one word per concept.
- Delivery follows plan → execute → review → verify; `/oh-my-claudecode:launch` is opt-in, invoked explicitly.
- Project skills: see "Project skills" below.
- Deferred surfaces (`docs/adr/`, `docs/standards/`, `docs/business/`, `scripts/`, `.mcp.json`) are created on first use, and each gets an index line here when it is created. `scripts/` and `.mcp.json` also need an allowlist entry in `src/guard/paths.ts` first.

## Credentials: `.env`

`.env` in the repo root holds the panel sign-in and server name. Never read, print, grep or source it: `bin/mc` loads it itself, and `.claude/settings.json` denies reading it. If `mc` reports a missing variable, ask the user to fix `.env`; the variable names are in `.env.example`:

- `PEBBLE_SFTP_HOST`, `PEBBLE_SFTP_PORT` (default 2022), `PEBBLE_SFTP_USER`: from the panel's Files → SFTP Credentials.
- `PEBBLE_PANEL_PASSWORD`: the game panel password, which is also the SFTP password.
- `PEBBLE_SERVER_NAME`: the server's display name. Use it when talking about the server; no command needs it.

## `bin/mc`

Paths are relative to the server root (`plugins/CrateReloaded/crates/vote.yml`); absolute paths and `..` are refused.

| Command | Does |
|---|---|
| `bin/mc ls [path] [-l]` | list one remote directory level; directories end in `/`. `-l` (`--long`) adds the size in bytes (`-` for directories) and the modtime (UTC) |
| `bin/mc pull <path>` | copy a remote file or directory into `server/<path>`, replacing the local copy, and record the remote listing |
| `bin/mc diff <path>` | unified diff remote → `server/<path>`; exit 1 when they differ |
| `bin/mc push <path>` | upload `server/<path>`; first copies the current remote version to `backups/<ts>/remote/<path>` |
| `bin/mc fetch` | copy the remote files named on stdin into `server/`, overwriting, with no backup or recorded listing; `bin/dev sync`'s incremental pull |

Exit codes: 0 ok, 1 differences found (`diff` only), 2 error.

- `pull` replaces `server/<path>` with the remote copy. If the local copy holds edits that were never pushed, it moves them to `backups/<ts>/local/<path>` first and says so.
- `push` refuses when the remote listing (size and modtime, 1-second precision) changed since the last `pull` of that same path. Pull again, then reapply the edits from `backups/<ts>/local/`. Listings are kept per path: after pushing `plugins/X/a.yml`, a push of `plugins/X` is refused until `plugins/X` is pulled again.
- `push` copies only: files deleted locally are not deleted remotely.
- `push` writes over the remote file in place, because PebbleHost's SFTP refuses the rename of a `.partial` upload. Run the plugin's reload only after `push` reports success. An upload that fails midway can leave the remote file truncated. To restore it: `bin/mc pull <path>` (your edits move to `backups/<ts2>/local/<path>`), copy the `backups/<ts>/remote/<path>` that the error names over `server/<path>`, `bin/mc push <path>`, then copy your edits back from `backups/<ts2>/local/<path>` and push again.
- `pull`, `diff` and `push` on the server root need `--all`; don't use it without the user asking.
- While the server runs, plugins rewrite their data files at any time. Push config files, not whole data folders.

`server/`, `backups/` and `.mc/` are git-ignored: server files can hold plugin database passwords and must not be committed to this public repo. Run `make hooks` once per clone; it covers every worktree. The pre-commit, pre-merge-commit and pre-push hooks run `bin/path-guard`, which refuses (exit 2) any path outside the public allowlist, any symlink, and any copy of a file under `server/`, `backups/` or `.mc/`. Never bypass it with `--no-verify`. If something leaks anyway, follow `docs/leak-response.md`.

### From a git worktree

Background sessions may edit files only inside their worktree. Run the worktree's own `bin/mc`; no override is needed:

- `.env` comes from the main checkout when the worktree has none (`MC_ENV_FILE` still wins).
- `backups/` is the main checkout's, so backups survive `git worktree remove`. Messages print its absolute path.
- `server/` and `.mc/` are the worktree's own: pull fresh into the worktree, edit there, and push from there. They are deleted with the worktree.

## `bin/dev`: local dev server

`bin/dev up` builds `mc-dev:<project>-<hash>` from the committed `server/` and boots it in Docker with no network access. `bin/dev restart` keeps server state, `bin/dev rebuild` boots a new commit on a fresh volume, `bin/dev reset` re-applies `/fixtures` (the merged fixtures, built databases included), `bin/dev boot-report` summarises the boot, `bin/dev join` lets a Minecraft client connect on `127.0.0.1:25565`, `bin/dev console <command...>` runs a server command over RCON and prints its reply (for example `bin/dev console list`; exit 2 with the reason when the pod isn't up; it never prompts), `bin/dev bot join NAME`, `bot chat NAME TEXT...`, `bot wait NAME REGEX [--timeout S]`, `bot quit NAME` and `bot list` drive headless offline players that stay joined between calls, and `bin/dev down` removes the pod. `up` and `rebuild` refuse uncommitted `server/` changes (exit 2); commit first. An untracked `server/` (the live copy pulled here) boots from a plain copy: `bin/dev up --jar purpur.jar --heap 6G`, then `bin/dev boot-report` compares it with the live `logs/latest.log`. Its output quotes server log lines, which may include player names, UUIDs and IPs: never paste it into a PR, issue or commit. The dev server generates a fresh world when `world*/` was not pulled. Dev images and `.dev/` hold the server's configs and secrets: never push or share them; `bin/dev down --all` removes the images. `console`, `bot` (except `list`) and `join` mark the pod's volume explored.

## `bin/dev sync`, `seed`, `inventory` and `sync-rules` (private repo)

`main` mirrors live. `bin/dev sync` keeps `main` checked out in its own worktree `.dev/sync` (the project itself works on another branch, usually `issue/N`). It pulls live's tracked roots there (`server.properties`, `bukkit.yml`, `spigot.yml`, `eula.txt`, `start.sh`, `config/`, `plugins/`, `libraries/`, `versions/`, `cache/`, root jars), minus what `sync-rules` excludes, and commits `live drift: <n> files` on `main` only when something changed. It refuses when `.dev/sync` is not on `main`, and runs the private path guard before committing. The first sync (or `sync --full`, or one whose stored listing is missing or no longer matches `main`'s `server/`) pulls every root whole. After that, every sync lists all those roots in one recursive call (`--checkers 16`, `MC_SYNC_CHECKERS` overrides; live's SFTP refuses heavier concurrency), compares it with the listing stored in `.dev/sync-listing.json`, downloads only new, resized and re-dated files through `bin/mc fetch`, and deletes files gone from live, pruning the directories that leaves empty. A file dated at or after the last listing's window (120 s before its start or the newest live mtime, whichever is earlier) is downloaded again, since a same-size rewrite in the same second keeps its modtime and the two clocks may differ: a sync with no change therefore re-fetches the newest files and makes no commit. A rule removed or added needs no full pull: the newly included files download and the newly excluded ones go. It prints its wall time, plus `OVER BUDGET` when an incremental sync with no changed files took over 30 s. rclone retries once. A file that live rewrites mid-copy therefore stops the sync (exit 2) instead of making it loop over re-downloads. The sync quotes rclone's lines naming the file, says to run it again, and commits no drift. A quieter moment usually gets through.

`sync-rules` (in the private repo root; defaults in `templates/sync-rules`) holds `<class> <pattern>` lines, gitignore-style and relative to the server root: `skip` is never transferred or committed (`plugins/ajLeaderboards/past-resets/`, `logs/`, ...), `data` is pulled only by `seed --with-data` and never committed (`*.db`, `userdata/`, ...), and `review` entries are proposals with no effect. Matching ignores case, like the private guard. Unmatched paths are synced and tracked. `sync` regenerates the `.gitignore` section from it, untracks files a new skip or data rule covers in their own `chore: untrack plugin data (<pattern>)` commit, and passes the rules to `bin/mc` as `MC_EXCLUDE_FILE` with `MC_EXCLUDE_IGNORE_CASE=1`, so rclone matches them ignoring case, with `**/` also matching zero directories. Other excludes (runbook push's) stay exact-case. After a full pull or a seed, anything the rules still cover is removed. The private guard refuses skip and data paths too.

`bin/dev seed N [--with-data PATH...] [--with-worlds] [--no-boot]` syncs, puts the project on `issue/N` (reusing it and its commits, or cutting it from the synced `main`; it refuses uncommitted work), replaces `.dev/seed-N` with fresh pulls of the opt-in paths, and boots a new pod with them as fixtures. A `--with-data` path that a skip rule covers is refused before anything runs. If the data paths held no files, the pod boots with no data fixtures. `bin/dev inventory [--wait S]` lists `plugins/` twice, S seconds apart (default 300), and commits `review` entries to `main`'s `sync-rules` for files that changed and data-like directory names. Make each one `skip` or `data`, or delete it.

## `bin/check`: recorded check runs

A check is a committed directory `checks/<id>/` with `profile.json` and `*.test.ts` files run by `node --test`. `profile.json` holds `kind` (`"e2e"` or `"bare-text"`) and, for e2e, optionally `fixtures` (directories in the check laid over the server on a volume's first boot; `bin/check run --fresh` boots with them), `data` (fixture paths that are plugin data; `*.db` always are), `needs` (`"console"`, `"bot"`), `restart` (the check calls `dev.restart()` or `dev.reset()`, which throw otherwise), `exclusive` (a pod of its own) and `sqlite` (`{"plugins/X/data.db": "x.sql"}`: wherever fixtures are merged, each committed SQL file of the check is run with `node:sqlite` into a new database at that server path, which is plugin data; a SQL error exits 2 naming the file, a target that is also a `fixtures` file is a conflict, and the fixtures hash covers each target and its SQL; `bin/dev up --fixtures` takes directories only). e2e checks import `dev` from `#harness/dev` (`dev.console(cmd)`, `dev.logSince(t)`, `dev.file(path)`, `dev.sqlite(path, sql, ...params)`) and `bot` from `#harness/bot` (`const b = await bot.join(name)`, `b.chat(text)`, `b.waitMessage(/re/)`, `b.quit()`, `bot.list()`; `bin/check run` and the suite make every bot leave before and after each check, so none leaks into the next); bare-text checks import only `test` and `bareText(file, path, literal)` from `#harness/unit`, which reads the file as committed, and the directory holds nothing but `profile.json` and `*.test.ts`. `bin/check run` resolves `#harness/*` itself and runs checks with a minimal env. `bin/check run <id>` runs one against the pod (e2e) or the committed `server/` (bare-text) and appends a record to `.verify/runs/issue-N.jsonl` (N from the branch `issue/N` or `--issue N`). The record carries the commit and hashes the running container was built from, not HEAD, so a fix counts only after `bin/dev rebuild`. `bin/check run <id> --fresh` rebuilds HEAD on a new volume first; only a red on such a volume will count, and no run on a volume touched by `bin/dev console` or `join` counts (the marker is inside the volume). `bin/dev up` and `rebuild` also refuse uncommitted harness image or relay changes. Commit `.verify/runs/`: the records are evidence. Exit 0 passed, 1 failed (recorded), 2 refused (nothing recorded): an uncommitted check, a file without tests, no pod.

The e2e loop: `bin/check run <id> --fresh` (red), commit the fix under `server/`, `bin/dev rebuild`, `bin/check run <id>` (green), commit `.verify/runs/`, then `bin/check gate <id>`. `bin/dev rebuild` keeps the fixtures and `sqlite` databases of the last boot; `--fixtures` replaces both. The gate exits 2 with each rule that failed unless a red and a later green of the same committed check for issue N hold rules G1-G10: the red is older than the green, the green booted a strict descendant commit that changed `server/`, nothing under `server/` or in the check changed after the green, both images were built from their commits with the same harness, check code and fixtures, the red ran on a `--fresh` volume, each was the first `bin/check run` on its volume (so no other check, and no `bin/dev console` or `join`, touched it first), HEAD descends from the green, and both record lines are committed unchanged. A bare-text check must also be nothing but `test(name, () => bareText(file, path, literal))` with a literal free of placeholders, color codes and tags, and the fix must touch every file it reads. The gate then re-runs the green on the running pod (it never boots one: `bin/dev rebuild` first, and the volume must not be explored) and records that confirm run, which must be the next run on the green's volume or the first on a new one; commit it too, since `postmortem` and `runbook` refuse an uncommitted confirm. The latest confirm run of the green decides. Only after a confirmed pass do `bin/check postmortem <id>` and `bin/check runbook <id>` write `docs/postmortems/` and `docs/runbooks/` from `templates/`; fill in their `<!-- -->` sections. G4 only sees that `server/` changed, not whether the change fixes anything: the postmortem's "Fix diff review" must justify every hunk of the diff. Rebuild before each green and before each gate: a red, a green and a confirm each count only as the first (or, for the confirm, the next) `bin/check run` on their volume, and the gate refuses without running when the pod's volume would not qualify.

The bare-text loop needs no pod and no `--fresh`: `bin/check run <id>` (red), commit the fix under `server/` (it must touch every file the check reads), `bin/check run <id>` (green), commit `.verify/runs/`, `bin/check gate <id>` (its confirm re-runs the check), commit the confirm record, then `postmortem` and `runbook`.

`bin/check suite` runs every committed check from a clean checkout and records nothing: bare-text checks first, then one pod (`suite0`, `suite1`, ...) per distinct merged fixture set with all its e2e checks. Checks share a pod only when their merged fixtures hash the same; checks with different fixtures get separate pods, and conflicting paths are refused within one check's own `fixtures` list (this replaces the plan's single merged profile with conflicts refused across checks). Between two checks on a pod it applies the fixtures again: with `data`, a restart that copies `/fixtures` over `/server` before the server starts; without, a copy of `/fixtures` over the running server, which neither deletes files a check created nor resets plugin state held in memory, so declare `data` for any plugin with state. `restart` checks run last on their pod; `exclusive` ones get their own. Each pod is torn down after its checks, pass or fail. The suite runs in a child process: on SIGINT or SIGTERM the parent kills it, removes every suite pod by label, and exits 130 or 143. If the parent itself was killed (SIGKILL), the next `bin/check suite` and `bin/dev down --all` stop the orphaned child (its group is in `.dev/suite.pid`, checked against `/proc` before any kill), and every `bin/check suite` first removes leftover suite pods. A check that can't run (a bad profile, conflicting fixtures, no tests) is reported `REFUSED` and the rest still run. It prints PASS/FAIL per check and a timings table (image cache hit, each boot, each check, each teardown, each refusal), writes `.dev/runs/<ts>/timings.json`, and prints `OVER BUDGET by Ns` past `checks/budget.json` (`{"seconds": N}`). Exit 0 all passed, 1 any check failed or was refused, 2 the suite itself was refused (dirty tree, no checks), 130/143 stopped by a signal.

`--target live` (for `bin/check run` and `bin/check suite`) runs the same checks read-only against the live server: `dev.file`, `dev.logSince` (the whole current `logs/latest.log`), `dev.sqlite` and `bareText` read through `bin/mc pull` into a throwaway `.dev/live/run-*` home (`MC_ENV_FILE`, else the project's `.env`, which only `bin/mc` reads), and the console, restarts and bots are refused. A test that hits them is skipped when the check's `profile.json` declares it (`needs: ["console"]` or `["bot"]`; a restart by `"restart": true`, `"exclusive": true` or the console need), and fails otherwise. The live target pulls only the exact files a check reads, into a 0700 home that is removed after the run. It lists the parent first and refuses a directory, a trailing `/`, or an empty or `.` segment before any copy. `dev.sqlite` pulls the db, `-wal` and `-shm` only when their listing (size, modtime) is the same before and after the pulls. It retries once, then refuses the run (exit 2, nothing recorded) with "live database changed during pull". `bin/check run` and `gate` run in a child process. On SIGINT or SIGTERM the parent kills the child's group (the check's `node --test` with it), removes the run's live home and exits 130 or 143. Each live run also starts by removing run homes whose owner process is gone, which covers a SIGKILL. A live run is recorded with `target: "live"`, never counts for the gate (the postmortem quotes the check's latest live record), and exits 2 with nothing recorded when no test ran; the live suite prints SKIP for such checks and exits 2 when none ran at all. This is the runbook's last step, after the push.

`bin/check runbook push N [--plan]` puts `issue/N`'s fix on live. It uploads only the `server/` files of `main...issue/N`, with the prefix stripped. Other paths (`checks/`, `docs/`) are printed as "not pushed", and deleted files are printed as manual steps. It needs the project on `issue/N`, the committed `docs/runbooks/<date>-N-<slug>.md`, and, for every committed `checks/N-*`, the same confirmed, committed gate pass that `postmortem` and `runbook` need (G1-G10, so no `server/` change after the green). It refuses a file that a `sync-rules` skip or data rule covers, anything under `server/` that is not a regular file on both sides (a symlink, a typechange, a submodule), and a name with a segment starting with `-` or holding a newline. `--plan` runs all of these checks too, so a plan that was OK'd is never refused at push. bin/mc takes the path after `--`. Before writing anything, it refuses if `main` changed any of those files after `issue/N` was cut, and it pulls each file into the persistent `.dev/runbook-N/home/` (0700), refusing if live's copy is no longer `main`'s. A new file goes up through the deepest directory live already has, with everything else there excluded. `--plan` stops after printing the set and the `bin/mc diff` of each file. Otherwise each file is pushed with `MC_RUNBOOK=1`, journalled in `.dev/runbook-N/journal.jsonl` with its backup under `.dev/runbook-N/home/backups/`, and the run stops at the first failure. `bin/check runbook rollback N` prints the restore commands of the last run (pull, copy the backup back, push), plus the new files to delete by hand. Run them only after the user's OK. In a private repo (`.harness-private` in `MC_HOME`, or in the superproject of the `harness/` submodule), `bin/mc push` refuses without `MC_RUNBOOK=1`.

`template/` is what a private server repo starts from:
- root wrappers `bin/mc`, `bin/dev` and `bin/check` that use the repo root and its `.env` (`bin/mc pull` is refused unless `MC_HOME` is under `.dev/`);
- `.gitignore` (with the section `bin/dev sync` generates from the default `sync-rules`), `.claude/settings.json` (the `.env` deny rules), `.harness-private`;
- `package.json`, which maps `#harness/*`;
- a `Makefile` (`setup`; `hooks` links `hooks/private-pre-push`, which refuses any remote not on `vcs.martinfrackerjr.com` (strictly `scheme://[user@]host[:port]/` or scp `[user@]host:`; a backslash or a second `@` is refused), and installs the submodule's guard; `test` refuses while either hook is missing);
- `CLAUDE.md`, which covers the loop from seed to live check.

## Taking a task

1. Locate: `bin/mc ls` from the root down (`plugins/`, the plugin's folder). Common places: `server.properties`, `bukkit.yml`, `spigot.yml`, `config/paper-*.yml`, `plugins/<Plugin>/config.yml` and the plugin's data folders, `logs/latest.log` for errors.
2. Pull only what the task needs. Don't pull `world*/` or `plugins/*.jar` unless asked: they are large. Before pulling a file that may be large, check its size with `bin/mc ls -l <dir>`.
3. Diagnose from the files and `logs/latest.log`. For plugin config questions, check the plugin's own documentation for the version in use (the version is in the jar name or the log's startup lines).
4. Edit under `server/`, then show the user `bin/mc diff <path>` and wait for their OK.
5. `bin/mc push <path>`, and tell the user what to run to apply it: the plugin's reload command, or a restart from the panel.

In the private server repo (the one with `.harness-private`, which has this harness as its `harness/` submodule), step 5 is different. Live writes go through `bin/check runbook push N` there, and `bin/mc push` refuses without `MC_RUNBOOK=1`. A bare `bin/mc push` is for using the harness alone, without a private repo. See `template/CLAUDE.md`.

## Project skills

`.omc/skills/<name>.md` holds OMC project skills; it is the only committed part of `.omc/` (`.gitignore` and the path guard allow exactly these files). `harness-live-evidence` times an unmerged harness change against live through the private server repo before its PR merges.

## Tests

Run `npm ci` once first. `make test-unit` (stubbed rclone, path-guard hooks in temp repos and `node --test test/ts/`, about a second), `make test-integration` (one shared `atmoz/sftp` Docker container for the whole run), `make test-dev` (`bin/dev` against vanilla Purpur in Docker, about a minute; downloads Purpur once), `make lint` (shellcheck and `tsc --noEmit`), and `make test-live` for a read-only `ls` against the real server.
